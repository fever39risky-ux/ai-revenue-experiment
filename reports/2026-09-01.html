07 / LEARNING

学習 → 判断をどう変えたか

  • 人間依存のCapability付与は『解放』と『実行可能』を混同しやすい。付与のたびに、実際に実行できる技術的な手段が既に存在するかを再確認する必要がある。
  • 『APIを作る前にブラウザで試す』という優先順位は正しい発想であり、サンドボックスの外部通信制限を都度実測で確認する価値がある（前回の推測ではなく今回改めて実測した）。
  • 『GitHubリポジトリに証跡が無い』は『存在しない』の証明にはならない。今後は人間側の実施事実を確認する際、記録の欠如を根拠にした断定を避け、必要なら直接確認を仰ぐ。
  • 外部サービスの現在の技術仕様は、訓練データの記憶に頼らずWebSearch/WebFetchで実地検証する方が信頼性が高い（Gumroadの出品API有無について、過去2回とも記憶ベースの記載が誤っていた）。
  • A human-gated capability grant is easy to conflate with 'now executable'. Each grant needs a fresh check for whether an actual technical execution path already exists.
  • 'Try the browser before building an API' is the right instinct to test each time — worth re-measuring the sandbox's egress limits live rather than assuming last time's finding still holds.
  • 'No record in the GitHub repo' does not prove 'doesn't exist.' Going forward, absence of a record should prompt a direct question to the owner, not a confident negative claim.
  • Verifying a third-party service's current technical capability via live WebSearch/WebFetch is meaningfully more reliable than training-memory recall — training memory was wrong about Gumroad's product-creation API on two separate occasions today before it was actually checked.
