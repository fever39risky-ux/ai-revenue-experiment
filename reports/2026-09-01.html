02 / DECISION

重要な判断と理由

  • オーナーの指摘通り、収益を止めている真のブロッカーとそれ以外のOptional Capabilityを区別する原則を採用（状態記録の正確性であり戦略変更ではない）。
  • Etsyショップ開通を受け、出品作業自体をオーナーに手動で依頼する選択肢は取らなかった（コピペオペレーター化禁止のルールに反し、かつAI実行可能な代替手段が存在するため）。
  • 既存の$9出品内容（価格・コピー・タグ・画像）は根拠のある市場データが無いまま変更しなかった。
  • Etsy出品を人間のセラー画面をブラウザ自動操作する方法ではなく、正式なEtsy API v3 + OAuthで構築した（Etsy利用規約・アカウントリスクの観点から）。
  • オーナーの『まずBrowser/Computer Useを試せ』という指示を、指示された通りに実際に検証してから結論を出した（API構築を先に正当化する形にはしなかった）。
  • Adopted the owner's principle of separating true revenue blockers from optional capabilities (a record-accuracy fix, not a strategy change).
  • On the Etsy grant, chose NOT to ask the owner to manually paste the listing (violates the standing 'not a copy/paste operator' rule, and an AI-executable path exists).
  • Kept the existing $9 listing content (price/copy/tags/images) unchanged — no market evidence yet justifies a different offer.
  • Built the Etsy integration on the sanctioned Etsy API v3 + OAuth path rather than browser-automating the human seller dashboard (ToS and account-risk considerations).
  • Actually tested the owner's 'try browser first' instruction rather than assuming the API path was already the right call — the conclusion follows from the test, not the other way around.

07 / LEARNING

学習 → 判断をどう変えたか

  • 人間依存のCapability付与は『解放』と『実行可能』を混同しやすい。付与のたびに、実際に実行できる技術的な手段が既に存在するかを再確認する必要がある。
  • 『APIを作る前にブラウザで試す』という優先順位は正しい発想であり、サンドボックスの外部通信制限を都度実測で確認する価値がある（前回の推測ではなく今回改めて実測した）。
  • A human-gated capability grant is easy to conflate with 'now executable'. Each grant needs a fresh check for whether an actual technical execution path already exists.
  • 'Try the browser before building an API' is the right instinct to test each time — worth re-measuring the sandbox's egress limits live rather than assuming last time's finding still holds.
