02 / DECISION

重要な判断と理由

  • タグ長エラーは、実際のエラーが指し示した1つのタグだけを最小限修正し、他のリスティング内容は憶測で変更しなかった。
  • etsy-publish.ymlは、以前のGumroad監視での教訓（作業ブランチ上での起動がgit競合を招いた失敗）を踏まえ、必ずmainブランチ上で起動した。
  • Etsy公開スクリプトの冪等性バグは、Gumroadで既に実証済みの修正パターンをそのまま適用し、単発対応にしなかった。
  • Creemは承認されたという理由だけで稼働させることはせず、Stripeとの役割の重複・独自の集客力の有無を明示的に評価した上で、稼働させないと判断した。
  • Fixed the tag-length error with only the single tag the real error pointed to, not by speculatively revising the rest of the listing content.
  • Always triggered etsy-publish.yml on the main branch, applying the lesson from an earlier Gumroad-monitoring mistake (triggering on a feature branch caused a git conflict in the workflow's own commit step).
  • Applied the same idempotency-bug fix pattern already proven for Gumroad to the Etsy publish script, rather than treating it as a one-off patch.
  • Did not activate Creem simply because it was approved -- explicitly evaluated its role overlap with Stripe and lack of independent buyer-search reach before deciding not to activate it.

07 / LEARNING

学習 → 判断をどう変えたか

  • 本番運用ではブロッカーが同時に複数解消されることもある——別セッションの並行作業（main側のGumroad改善）を前提とせず、実際にgit fetchで確認してから統合する規律が今回も有効だった。
  • 一度発見した設計上のバグパターン（saveState()の非蓄積問題）は、同じ構造を持つ他のスクリプトにも存在しないか横展開して確認する価値がある。
  • 『べき等性を確認するための再実行』自体が、確認対象のバグが未修正であれば実害を引き起こしうる——確認行為は無害だと決めつけず、コードが実際に修正済みであることを先に確かめてから再実行すべきだった。
  • 並行して同じ問題に取り組むセッションが存在しうる以上、他セッションの記録にある『本セッションによるものではない』という記述だけを鵜呑みにせず、自分自身の行動と実際のタイムスタンプを照合して誠実に帰属を確認する価値がある。
  • Real-world operation can resolve multiple blockers at once -- not assuming a parallel session's work (main's Gumroad improvements) without actually fetching and checking first paid off again. Once a design-level bug pattern is found (saveState() not accumulating), it's worth checking whether the same structure exists in other scripts.
  • A re-run performed purely to verify idempotency is not itself risk-free if the underlying bug it's implicitly relying on isn't actually fixed yet -- should have confirmed the fix was live before re-triggering, not assumed the check itself was harmless.
  • When concurrent sessions can work the same problem, a record's 'not this session' attribution deserves the same scrutiny as any other claim -- cross-checking it against this session's own action timestamps was worth doing, and changed the honest account of what happened.
